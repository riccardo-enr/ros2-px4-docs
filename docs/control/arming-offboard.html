Arming and Offboard Mode

Before a ROS 2 node can send setpoints to PX4, the vehicle must be armed and PX4 must be in offboard mode. Both transitions are triggered by publishing VehicleCommand messages. The sequence has strict ordering requirements and timing constraints.

Required sequence

1. Start streaming OffboardControlMode heartbeat  (>=2 Hz, before switching)
2. Start streaming setpoints                       (same rate as control loop)
3. Send VehicleCommand: VEHICLE_CMD_DO_SET_MODE -> OFFBOARD
4. Send VehicleCommand: VEHICLE_CMD_COMPONENT_ARM_DISARM -> ARM

Steps 1–2 must begin before step 3. PX4 rejects the offboard mode switch if it has not already seen a recent OffboardControlMode message. Keep both streams running continuously thereafter.

VehicleCommand helper

/* vehicle_command.hpp */
#pragma once
#include <rclcpp/rclcpp.hpp>
#include <px4_msgs/msg/vehicle_command.hpp>

inline void send_vehicle_command(
    rclcpp::Publisher<px4_msgs::msg::VehicleCommand>::SharedPtr& pub,
    rclcpp::Node* node,
    uint32_t command,
    float param1 = 0.0f,
    float param2 = 0.0f)
{
    px4_msgs::msg::VehicleCommand msg{};
    msg.timestamp       = node->get_clock()->now().nanoseconds() / 1000;
    msg.command         = command;
    msg.param1          = param1;
    msg.param2          = param2;
    msg.target_system   = 1;
    msg.target_component = 1;
    msg.source_system   = 1;
    msg.source_component = 1;
    msg.from_external   = true;
    pub->publish(msg);
}

Switching to offboard mode

#include <px4_msgs/msg/vehicle_command.hpp>

/* PX4_CUSTOM_MAIN_MODE_OFFBOARD = 6 */
send_vehicle_command(
    vehicle_cmd_pub_, this,
    px4_msgs::msg::VehicleCommand::VEHICLE_CMD_DO_SET_MODE,
    1.0f,   // base mode: custom
    6.0f);  // custom main mode: offboard

PX4 switches only if it has received OffboardControlMode messages recently. If the switch fails, VehicleStatus.nav_state stays at its prior value.

Arming

send_vehicle_command(
    vehicle_cmd_pub_, this,
    px4_msgs::msg::VehicleCommand::VEHICLE_CMD_COMPONENT_ARM_DISARM,
    1.0f);  // 1.0 = arm, 0.0 = disarm

Disarming

send_vehicle_command(
    vehicle_cmd_pub_, this,
    px4_msgs::msg::VehicleCommand::VEHICLE_CMD_COMPONENT_ARM_DISARM,
    0.0f);  // disarm

Monitoring vehicle state

Subscribe to VehicleStatus to read the current arming and nav state:

#include <px4_msgs/msg/vehicle_status.hpp>

auto qos = rclcpp::QoS(10).best_effort();

status_sub_ = create_subscription<px4_msgs::msg::VehicleStatus>(
    "/fmu/out/vehicle_status_v1", qos,
    [this](const px4_msgs::msg::VehicleStatus::SharedPtr msg) {
        armed_       = (msg->arming_state ==
                        px4_msgs::msg::VehicleStatus::ARMING_STATE_ARMED);
        in_offboard_ = (msg->nav_state ==
                        px4_msgs::msg::VehicleStatus::NAVIGATION_STATE_OFFBOARD);
    });
Note

The topic is /fmu/out/vehicle_status_v1 (versioned) from PX4 v1.14 onward. See Versioned topic names.

Relevant VehicleStatus constants:

Field Constant Value
arming_state ARMING_STATE_DISARMED 1
arming_state ARMING_STATE_ARMED 2
nav_state NAVIGATION_STATE_OFFBOARD 14

Full arming state machine

A typical controller node follows this pattern on startup:

/* Called at ~10 Hz in the main control timer */
void control_loop()
{
    /* 1. Always publish heartbeat first */
    publish_offboard_control_mode();

    /* 2. Always publish a setpoint (zeros are fine pre-arm) */
    publish_setpoint();

    /* 3. After a short warm-up, switch mode and arm */
    if (!mode_sent_ && ++tick_ > 10) {   // ~1 s at 10 Hz
        switch_to_offboard();
        arm();
        mode_sent_ = true;
    }
}

The tick counter gives PX4 time to receive a few heartbeats before the mode switch is requested.

Takeoff after arming

After arming, the vehicle is on the ground with motors spinning at idle. Command a TrajectorySetpoint with a target altitude to begin the takeoff:

px4_msgs::msg::TrajectorySetpoint traj{};
traj.timestamp = get_clock()->now().nanoseconds() / 1000;

/* NED frame: negative z = above ground */
traj.position  = {0.0f, 0.0f, -2.0f};  // 2 m above ground
traj.yaw       = 0.0f;                  // North-facing
traj_pub_->publish(traj);

Use OffboardControlMode with position = true while climbing:

mode_msg.position = true;
mode_msg.velocity = false;
mode_msg.attitude = false;

Switch OffboardControlMode fields to match whichever control mode you activate once at altitude. See Low-Level Offboard Control.

Safety: continuous stream requirement

PX4 exits offboard mode if the OffboardControlMode stream stops for more than ~500 ms. It also disarms if the vehicle is commanded with zero throttle while on the ground in offboard mode for more than ~1 s.

Keep two independent timers:

// Heartbeat: 10 Hz is safe margin above the 2 Hz minimum
offboard_timer_ = create_wall_timer(100ms, [this]() {
    publish_offboard_control_mode();
});

// Control output: 100 Hz
control_timer_ = create_wall_timer(10ms, [this]() {
    publish_setpoint();
});

The timers are independent so a slow control computation does not starve the heartbeat.

Troubleshooting

Vehicle never arms

  1. Check pre-arm checks: ros2 topic echo /fmu/out/vehicle_status_v1 | grep arming.
  2. In SITL, the EKF2 estimator must be healthy before arming. Wait ~5 s after SITL starts.
  3. Ensure OffboardControlMode is being published before sending the arm command — PX4 refuses to arm for offboard if no heartbeat has arrived.

Offboard mode switch is accepted but vehicle falls

The OffboardControlMode was set with position = true but no TrajectorySetpoint is being published. The position controller has no target and commands zero thrust. Always publish a setpoint at the current position immediately after arming.

Vehicle disarms immediately after takeoff

The motor output stream (ActuatorMotors) stopped. PX4 exits offboard mode and auto-disarms. Check that your control timer is running without exceptions.
